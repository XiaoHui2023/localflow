# 调度容量与整体性能评估

## 发现与优化

- 默认 `max_concurrency=4` 是与服务器能力无关的人为瓶颈；改为 `auto`，按 CPU affinity、cgroup quota 和逻辑 CPU 结算，仍可显式配置 1–4096。
- `Store.list_tasks()` 曾把任何请求静默截到 500。它不仅限制调度观察，还意味着服务退出请求的 `limit=10_000` 实际只看到 500 个任务。上限已提高到受控的 10,000；调度活动集按有效并发完整读取。
- 退出清理不能假设排队记录少于一页。现按可中断状态分批排空，机器夹具用 10,005 个排队任务证明第二页也全部取消；重启恢复固定覆盖完整受支持活动集，即使重启后用户调低并发也不会漏掉旧进程。
- “历史日志总保留量 ≥ 并发数 × 单任务日志上限”曾是错误的启动门槛：保留量负责终态淘汰，不应限制活跃任务数量。该耦合已删除，单任务文件上限继续控制每个活跃任务的磁盘增长。
- 调度器只看最早 500 个排队任务时，500 个共享互斥键的任务会遮住后方完全独立的任务。现改为有界推进游标：每轮扫描有限数量、跨轮继续、到尾回绕。回归夹具以 501 个阻塞任务加一个独立任务证明第二轮即可取得后者。
- 首版游标把 Pydantic datetime 直接交给 SQLite，适配器生成空格分隔时间而数据库保存 `T` 分隔 ISO，导致词法分页回到同一页；测试自然失败后改为显式 `isoformat()`，回归通过。
- 页面切换、浏览器/控制器空闲资源、大日志内存边界已有独立预算；不能用其中一个指标替代其它所有者。
- 构建审计发现旧浏览器初始入口为 3.18 MiB、gzip 约 829 KiB，主要由启动时静态导入 Monaco 造成。将编辑器、语言贡献和 worker 初始化拆为按需分包后，普通页面初始入口降为约 806 KiB、gzip 约 221 KiB（约减少 73%）；Monaco 分包仅在编辑/冲突界面加载。最终精确值由浏览器收据和质量脚本从同一构建资产复算。

## 直接门禁

- 自动容量单测注入 64 个 host CPU、12 个 affinity CPU，必须结算为 12；4096 可显式配置，4097 被拒绝。
- 501 个互斥阻塞任务不能永久遮住后方独立任务；测试同时要求夹具入队 <15 s、两轮扫描 <3 s。
- 10,005 个排队任务的退出夹具必须跨页调用 10,005 次取消且最终无活动状态；恢复查询必须读取 10,000 条完整支持页，而非沿用当前较小并发值。
- 状态 API 返回 `configured_max_concurrency` 与有效整数 `max_concurrency`。
- Linux systemd/PTY、完整 cgroup 停止、冻结程序退出继续作为任务独立性与残留进程门。
- Edge 收据继续记录控制器 RSS/CPU、浏览器 JS 堆/任务时间/DOM/监听器/请求/WebSocket；终端历史使用 4 MiB 浏览器窗口和服务端分块搜索。

## 结论边界

LocalFlow 现在默认使用服务获得的全部 CPU，不再固定只跑四个；独立且无互斥冲突的任务会在有效额度内并行。每个任务的生命周期与进程树隔离，但共享服务器物理资源不可能在任意过量并发下“互不影响”。CPU 密集任务用自动值；I/O 等待多的任务可实测提高；任务自身多线程时应降低任务数。现场用 cgroup accounting 与 PSI 区分控制器开销、单任务开销和真实资源争用。
