# LocalFlow plugin development

Read `../../docs/plugins.md` and `../../plugins/README.md`. Start from the closest existing plugin in `../../plugins/`; do not fork the host UI for one plugin.

## Contract

- Register one plugin with the provided decorator.
- Declare a configuration model, a strict input model matching the finite `run_fields` schema, status definitions, and one API example that expands successfully. A configuration model describes only plugin-owned fields; the host validates only those declared fields and always preserves arbitrary site-owned top-level keys for configlib variables and `expand`. The complete configuration and plugin-fields schemas therefore allow additional properties. In contrast, the per-run input model remains closed and rejects keys outside `run_fields`.
- Discovery returns data; it does not render components. The host owns controls, accessibility, layout, and responsive behavior.
- Optional `inspect(values, context)` returns read-only values and diagnostics; the host owns the compact component and tooltip. Set `check: "availability"` only for an input that must exist now. The host shows a failure cross only for an unavailable error and shows no success decoration. Keep inspection bounded, side-effect free and valid for both web and API callers.
- Keep editor syntax/import diagnosis separate from plugin diagnosis. Saving an ordinary configuration file never requires the plugin schema to pass. The plugin run surface owns resolved-value review and runnable errors.
- Validate common task fields and declared plugin fields from the fully resolved include/variable tree, the same representation passed to expansion. A placeholder string can resolve to `null` or another incompatible type; rejecting it only inside `TaskCreate` is a late-validation defect. Treat explicit `null` on optional common fields as absent, preserve site-owned null values, and report an error only when such a value reaches a required or typed task/plugin field.
- Inspection must show every consequential value, including the complete command, working directory, case/simulation paths, labels, mutex keys, configured output/log paths and operator-facing custom text. Do not add a derived row such as a string command's first token when the complete command already answers the question. Check only inputs that must already exist. Do not reject or warn merely because an output or log file is expected to be created by the forthcoming run. Repeated operator text is a list of independent copy targets: keep runtime placeholders stable in run review, freeze resolved values into each task, and preserve them when result evaluation replaces calculated fields.
- Expansion returns independent `TaskCreate` records. When a value must be unique across requests or restarts, return `TaskDraft` with a host-owned `DeferredValue`; never edit a queued task or allocate a global sequence inside the plugin. Use mutex keys for scheduling, not display tags alone.
- Prefer string commands in examples and configuration; LocalFlow gives them Ubuntu shell semantics. Accept exact argv lists for callers that must bypass the shell. Stable commands belong in configuration and normally do not appear in `run_fields`.
- Result evaluation must use final authoritative output, include only files that exist, and return plugin-defined status keys. Optional evidence fields must preserve absence semantics: do not render an empty inspection row, infer a phase failure for an unconfigured phase, or claim domain success/failure when its evidence source was not configured. Keep internal calculation inputs under underscore-prefixed custom keys.
- A stop strategy is bounded and replayable. It may send signals, terminal input, or a fixed command, but terminal state still waits for executor confirmation.

Run the plugin tests and at least one real finite or interruptible example before handing it off.

## Composing verification configuration

For AI-authored verification configuration, fetch `/api/v1/plugins/verification` and start from `api.example`; validate configuration and inputs against their separate JSON Schemas instead of inventing field names. Keep stable command, Case source, directory, labels, mutex and any available log templates in configuration; compile and run log lists are independently optional and must be omitted rather than invented when the tool does not produce them. Put selected cases, per-case counts and an optional seed in run inputs. Case candidates belong to the plugin discovery contract: use `case_names` for configuration-derived candidates or `case_directory` for an explicitly managed external directory; never assume the host creates a shared `cases/` tree. The plugin exposes only `${case}` and `${seed}`; use either, both, or neither. Every other placeholder must resolve from the configlib YAML tree after includes are merged. Never assume `root`, `scripts_dir`, `run`, `runs`, or `cases` exists. Call the plan endpoint before submission, then submit once with an idempotency key. The public error status is exactly `ERROR`; counts remain parser evidence and never enter the label or calculated detail. Without configured run-log evidence, the neutral result is `finished`/“运行结束”, never a guessed verification pass or failure.

This variable boundary is universal, not verification-specific. Command and third-party plugins may accept arbitrary site-owned top-level keys, nested objects, and `variables` entries; all remain available to configlib and `expand`. LocalFlow must never synthesize `root`, `scripts_dir`, `cases_dir`, or run-input variables for them. A plugin may declare only `case` and/or `seed` as deferred placeholders; reject any other deferred name at plugin load so a configuration stays portable and unknown-variable diagnosis remains honest.
